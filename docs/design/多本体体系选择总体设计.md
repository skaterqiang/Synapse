## 0. 基本概念

> 本节统一定义全文术语：先给**通用定义**（业界共识），再给**本系统中的作用**（Synapse 里的具体形态）。

### 0.0 一个例子串起所有概念：「充电桩扩容」

> 先用一个人人都能懂的故事，把知识图谱、本体、类、谓词、约束、体系、推理、术语归一全部串一遍。后续每节的正式定义都可以回看这个例子。

**背景**：你所在的小区要申请停车位充电桩扩容。物业丢给你三份文档：《供电容量说明》《申请材料清单》《施工安全规范》，让你评估方案是否可行、要准备哪些材料。

> **角色说明**：本例的第二人称「你」= **业主/住户一方**，即 Synapse 的使用者（全文「用户」角色）；**物业**只是外部资料提供方/需求触发者，不参与系统操作。三份文档进入系统后即为**原始文件（raw）**。各角色与系统职责的完整对应见 §13.3。

**第一步：建本体（立规则）。** 你先在 Synapse 里选择 **ISO 15926 体系**（§2.3）——它天生适合「设备/活动/时间段」这类工业对象。体系自带的**类树**告诉你：世界上所有东西要么是「可能个体」（physical_object 物理对象、activity 活动、period_in_time 时间段），要么是「抽象对象」（class 类别、relationship 关系）。你又在这个**本体基座上**加了两个领域类：`充电桩`（挂在 physical_object 下）、`申请材料`（挂在 abstract_object 分支下——注意 information 信息体是 bfo-lite 的类，ISO 15926 没有 information 类，跨体系举例时不能混用类名）。**本体就是你给 AI 立的规矩：这个世界里有哪些类、类之间能连什么关系。**

**第二步：提取知识图谱（把文档变成网）。** 把三份文档丢进提取队列，体系下拉选「ISO 15926」。LLM 按本体的类表和**谓词表**逐批阅读文档，产出三元组：

```
变压器 —composedOf→ 低压配电柜
充电桩 —connectedTo→ 变压器
扩容申请 —classifiedBy→ 高压新装活动
扩容申请 —containedIn→ 申请材料清单
```

每个三元组里：主语和宾语是**实体（节点）**，中间的动词是**谓词**。这些三元组连起来就是**知识图谱**——三份文档不再是三堆文字，而是一张能算的网络。注意每个节点都带着出处（`sources[]` 记的是哪份文档哪段话），这就是**证据**的雏形。

**第三步：约束校验（守住合规）。** 你在本体里登记了三条**约束**（五元组：主体+属性+条件+值+说明）：

1. `变压器 · 容量 ≤ 630 kVA`（超出要换更大的，费用翻倍）
2. `充电桩群 · 同时使用率 ≤ 0.8`（经验安全值）
3. `扩容申请 · 申请材料 ≥ 3 项`（基数约束，少一项直接退回）

方案草稿进来后，`validateGraphConstraints` 逐条硬校验——**方案里的数字不是 AI 猜的，是被约束反推出来的**：20 个车位 × 7kW × 同时使用率 0.8 = 112kW，加上小区现有负荷 380kW，合计 492kW < 630kW，第 1 条通过；材料只附了 2 项，第 3 条**拦截**并提示缺什么。这就是约束的价值：把「什么才算合规」从事后扯皮变成事前拦截。

**第四步：问答与推理（先想后取）。** 你在问答页问：「**变压器出问题会影响什么？**」——这个问题**答案不在任何一份文档里**，而在文档之间的**关系**里。系统先抽取实体「变压器」匹配到图中节点，沿 `composedOf / connectedTo` 谓词做正向遍历（**影响面分析**）：变压器 → 低压配电柜 → 充电桩群 → 20 个车位。推理器再自动补齐隐含关系：充电桩 `connectedTo` 变压器成立，则**逆关系** `connectedFrom` 自动成立；如果谓词标了**传递**特性，「A 是 B 的部件、B 是 C 的部件」会自动推出「A 是 C 的部件」（标注 `inferred:true`，能分清哪条是人录的、哪条是机器推的）。

**第五步：术语归一（十种说法一个节点）。** 文档里「变压器」「配变」「10kV 配电变压器」「transformer」是同一个东西。**术语归一**（aliases）把它们收敛到一个节点——否则问「配变容量」就漏掉了只说「变压器」的那段文档，这就是检索漏召的根源。

**第六步：换体系重提（体系可切换）。** 物业觉得 ISO 15926 太重，你改用 **bfo-lite 简化版 BFO** 重新提取同一份文档：变压器归为 `object`，扩容申请归为 `information`，施工过程归为 `process`——9 个类够用、prompt 更短更准。两版图谱按体系分组共存、可对比，差的版本一键清除。**这就是多体系的意义：工具跟着问题走，而不是问题迁就工具。**

> **一句话总结**：本体立规则（类+谓词+约束）→ 提取把文档编译成图谱 → 约束守住合规 → 推理补齐隐含关系 → 术语归一消除漏召 → 问答沿关系「先想后取」。

### 0.1 知识图谱（Knowledge Graph）

**通用定义**：以三元组（主语–谓词–宾语）为最小单位，把对象、对象间的关系、以及「什么才算成立」的规则组织成一张可计算的网络。它不是「更好的搜索」，而是一份能被机器执行的领域词典加约束系统。

**本系统中的作用**：Synapse 图谱存于 kv `'graph'`（nodes + edges）。节点带类型/描述/来源引用（`sources[]` 指回笔记与原始文件），边带谓词。作用有三：

1. **关系推理**——回答「谁依赖谁、A 故障影响哪些」这类答案不在任何单篇笔记里的问题（先想后取：先在图里毫秒级推理出需要哪些笔记，再去取原文）；
2. **检索增强**——KG 问答（kgAsk）把实体子图作为上下文注入 LLM prompt，替代纯向量检索；
3. **知识沉淀**——提取流水线把文档编译为结构化节点，延迟与库规模解耦。

### 0.2 本体（Ontology）

**通用定义**：一个领域的形式化规范——定义该领域有哪些类（Class）、类间层级（is_a）、可用关系、以及约束。是图谱的「棋盘规则」（TBox），与不断增长的事实数据（ABox）分两层管理。

**本系统中的作用**：本体 = 类表 + 谓词表 + 约束表，存于 kv `'ontology'`。作用：

1. **约束提取**——提取 prompt 中的类型表/谓词表直接来自本体，LLM 只能在本体划定的范围内归类与连线（不越界、不乱造类型）；
2. **组织浏览**——图谱着色、类型筛选、结构图都按本体层级分组；
3. **体系抽象**——本设计的核心：本体由可切换的顶层体系（bfo-lite / bfo / iso15926 / owl:*）+ 用户扩展层合成，见 §2–§4。

### 0.3 类 / 实体类型（Class / Entity Type）

**通用定义**：对具有共同特征的对象的抽象（如「物体」「过程」），类间以 is_a（subClassOf）构成层级树。

**本系统中的作用**：节点必有 `type` 字段且必须是本体类表中的 key（未知类型降级为体系的 fallbackType）。类决定：图谱节点颜色分组、提取时的归类选项、问答时的本体角色标签（如 `[bfo-lite·object]`）。本系统中类带 `parent` 指针构成体系树（§2），结构图（§7.1）即类树的可视化。

### 0.4 谓词（Predicate / Relation Type）

**通用定义**：连接两个节点的关系类型，是三元组的「动词」。设计原则：双命名（中文 label + 机器 code）、domain/range 限定主宾类型（护栏）、特性标注（传递/对称/互逆/单值）。

**本系统中的作用**：边必有 `rel` 字段且应在本体谓词表内（未知谓词降级为 fallbackRel）。**实体决定「能提到谁」，谓词决定「能问出什么」**——有了「依赖」谓词才能做影响面分析（D4），有了传递特性才能自动补全推理链（D3）。谓词是可复用资产：8 个内置中文谓词 + 各体系的标准谓词集（RO 子集 / Part 7 模板），用户可叠加自定义谓词。

### 0.5 约束（Restriction / Constraint）

**通用定义**：「什么才算合规」的可执行断言——带主体、属性、条件、数值/基数。真实项目中约束数量往往远超关系数量（典型比例 实体72 : 关系43 : 约束135），业务的难点从来不是「有什么对象」，而是「什么才算成立」。

**本系统中的作用**：约束以五元组 `{subject, attr, op, value, desc}` 表达（§8），由 `validateGraphConstraints` 对节点属性逐条硬校验（三期）。作用：

1. **合规校验**——方案参数是否越界（如 D5 充电桩扩容的容量上限）；
2. **关联完整性**——基数约束守住流程材料完备（如申请材料≥3 项）；
3. **生成护栏**——方案生成时参数必须落在约束区间内，「数字是被约束反推出来的，不是模型猜的」。

### 0.6 顶层本体 / 本体体系（Top-Level Ontology / Profile）

**通用定义**：跨领域通用的最上层概念框架（BFO、ISO 15926、SUMO、UFO 等），领域本体在其下挂载扩展。顶层体系的选择决定类树的组织哲学（如 ISO 15926 的 4D 时空观）。

**本系统中的作用**：即本设计的 **TopOntologyProfile**（§2）——内置 bfo-lite / bfo / iso15926 三个只读基座 + OWL 导入自定义体系。作用是让同一份文档可按不同抽象级别提取，提取时在弹窗中选择（§3 优先级），节点带 `profile` 字段实现混合体系共存。

### 0.7 实体与节点（Entity / Node）、边（Edge）

**通用定义**：实体是本体类的实例（ABox 事实），在图中即节点；边即一条实例化关系。

**本系统中的作用**：节点 schema `{id, name, type, desc, sources[], domain, profile}`，id 为小写名、name≤40 字、desc≤120 字、sources≤5 条（`笔记·X` / `原始·X` 标签支持回溯原文）；边 schema `{from, to, rel}`，按 (from,to,rel) 去重、禁自环。推理产生的边带 `inferred:true / inferredFrom[]`，前提被删时级联清理（三期）。

### 0.8 推理（Inference / Reasoning）

**通用定义**：由已知事实按规则自动推导新事实——传递闭包、对称、逆属性、Functional 单值校验等。

**本系统中的作用**：`reason.js` 四个轻量推理器（三期）：传递闭包（依赖链补齐）、逆关系（双向查询）、对称关系、Functional 冲突检查 + 沿「依赖」边的影响面分析（D4 的根因定位即此）。关键设计：**推理依赖谓词特性而非类层级深度**，因此与选用哪个体系正交，bfo-lite 也能做。

### 0.9 术语归一与证据（Aliases & Evidence）

**通用定义**：术语归一 = 同义词/缩写/别名收敛到唯一节点（消除漏召）；证据 = 每条断言标注来源与权重（OWL 导入 1.0 > 人工确认 0.9 > 模型抽取=置信度），冲突进冲突组而非互相覆盖。

**本系统中的作用**：节点带 `aliases[]`（D1/D7 演示术语归一）；`status` 走六态机 pending/accepted/conflicted/deprecated/rejected/superseded（D8 演示冲突裁决）。现有 `sources[]` 已是证据雏形，三期补齐权重与状态。

## 1. 背景与目标

当前 Synapse 知识图谱使用一套固定的扁平本体（5 个类、8 个中文谓词），存于 kv `'ontology'`。参考《知识图谱顶层本体结构图》《知识图谱：从概念到落地》两份文档后，确定引入**可选的顶层本体体系（TopOntology Profile）**机制：

- 不同文档/领域适合不同抽象级别的顶层本体；
- 个人知识库默认使用轻量的 bfo-lite，避免过度工程化；
- 需要严谨推理或工业数据集成时，可切换标准 BFO 或 ISO 15926。

**设计原则**

1. Profile 为**内置只读基座**，用户层在其上叠加（同 key 覆盖）；
2. 老数据**零损失迁移**（中文谓词 key 保留）；
3. 同一图谱**允许混合体系节点共存**，按 profile 分组浏览；
4. 提取 prompt 预算有限（约 6000 字/批次），大体系采用**两阶段 prompt**。

## 2. 核心概念：TopOntologyProfile

每个 profile 是自包含的只读内置基座：

```
TopOntologyProfile = {
  id, name, desc,
  classes:     [{ key, label, code?, parent, desc, examples[] }],   // parent 构成树
  predicates:  [{ key, label, code?, domain?, range?, features?[], desc }],
  constraints: [...],        // 体系级约束说明
  fallbackType,              // 该类体系下的兜底类型（root）
  fallbackRel,               // 兜底关系
  promptMode: 'flat' | 'two-stage'
}
```

### 2.1 bfo-lite（默认，11 类，flat prompt）

```
thing
├─ continuant 持续体
│   ├─ object 物体
│   ├─ quality 性质
│   └─ realizable 可实现体
│       ├─ role 角色
│       └─ function 功能
└─ occurrent 发生体
    ├─ process 过程
    ├─ event 事件
    └─ information 信息体
```

- fallbackType: `object`；fallbackRel: `相关`
- 谓词沿用现有 8 个中文 key（属于/包含/依赖/相关/引用/应用于/衍生自/矛盾于）+ RO 常用子集
- prompt 一次性输出全部类型表

### 2.2 bfo（标准 BFO 2020，21 类，two-stage prompt）

```
entity
├─ continuant
│   ├─ independent_continuant
│   │   └─ material_entity → object, object_aggregate, fiat_object_part ...
│   ├─ specifically_dependent_continuant
│   │   ├─ quality
│   │   └─ realizable_entity → role, disposition, function
│   └─ generically_dependent_continuant
└─ occurrent
    ├─ process → history, process_boundary
    ├─ temporal_region
    └─ spatiotemporal_region
```

- 谓词采用 RO 子集 14 个 + 兜底 `related_to` 共 15 个：`is_a / instance_of / part_of / has_part / participates_in / has_participant / inheres_in / bearer_of / located_in / occurs_in / precedes / realizes / has_role / derives_from / related_to`
- 两阶段 prompt：先分 continuant/occurrent 大类，再在子树内细分

### 2.3 iso15926（4D 三维时空观，14 类，two-stage prompt）

```
thing
├─ possible_individual 可能个体
│   ├─ physical_object → whole_life_individual, arranged_individual
│   ├─ activity 活动
│   ├─ event 事件
│   └─ period_in_time 时间段
└─ abstract_object 抽象对象
    ├─ class → class_of_class, class_of_individual
    ├─ number 数
    └─ relationship 关系
```

- 谓词采用 Part 7 模板 13 个 + 兜底 `relatedTo` 共 14 个：`classifiedBy / hasSuperclass / hasClassMember / temporalPartOf / spatialPartOf / composedOf / startsBefore / endsBefore / existsAt / involvedIn / connectedTo / containedIn / representsIn / relatedTo`

### 2.4 自定义 OWL 2 导入（`owl:<name>`）

支持导入 OWL 2 格式的本体定义文件（`.owl` / `.rdf` / `.ttl`），解析后生成一个自定义 profile：

- **入口**：本体页「导入 OWL」按钮，选择本地文件；
- **解析**（`src/main/graph/owl.js`，二期）：
  - 支持 RDF/XML 与 Turtle 两种序列化；
  - 提取 `owl:Class` → classes（`rdfs:subClassOf` → parent，`rdfs:label`/`skos:prefLabel` → label，`rdfs:comment` → desc，`owl:deprecated` 跳过）；
  - 提取 `owl:ObjectProperty` → predicates（`rdfs:domain`/`rdfs:range`，`owl:TransitiveProperty`/`SymmetricProperty`/`FunctionalProperty`/`InverseFunctionalProperty` → features，`owl:inverseOf` 配对）；
  - 提取 `owl:AnnotationProperty` 忽略；基数/值约束（`owl:Restriction` + `owl:cardinality`/`hasValue`/`someValuesFrom`）→ constraints 说明项；
  - 解析深度：仅直接定义，**不做本体推理/闭包展开**；超大本体（类 > 200）截断并提示，仅保留前两层子类树；
- **生成 profile**：`id = 'owl:' + 文件名slug`，`promptMode` 按类数自动判定（≤12 类 → flat，否则 two-stage，顶层取无 parent 的根类集合），fallbackType = 根类中 label 最通用者（否则首个根类），fallbackRel = 首个谓词；
- **存储**：导入结果整体存入用户层（见 §4 扩展），**不内置固化**，可删除；源文件复制到 `data/ontology/` 留存以便重新导入；
- **限制说明**（UI 明示）：导入体系不参与跨体系映射表；SHACL/SWRL 规则不执行，仅作为 constraints 文本展示。

## 3. 体系选择优先级

提取时按以下优先级决定使用哪个 profile：

1. **提取弹窗下拉框**（跟随领域模版 / bfo-lite / bfo / iso15926）—— 用户当次指定
2. **领域模版字段** `ontologyProfile` —— 模版绑定（如「工业设备」模版绑 iso15926）
3. **全局设置** `settings.ontologyProfile`（默认 bfo-lite）
4. **案例固定绑定**（案例中心预置，见 §8）

## 4. 存储：kv schema v3

```
kv 'ontology' = {
  profileId,               // 当前编辑查看的基座
  userClasses: [],         // 用户自定义类（叠加层）
  userPredicates: [],
  userConstraints: [],
  actions: [],             // 见 §8（二期/三期）
  owlProfiles: []          // 导入的 OWL profile 数组，元素即完整 TopOntologyProfile
}
```

- 运行时 `resolveOntology(profileId?)`：
  - `profileId` 以 `owl:` 开头 → 从 `owlProfiles` 查找，找不到回退 bfo-lite 并告警；
  - 否则 = `ONTOLOGY_PROFILES[profileId]` 深拷贝；
  - 再叠加用户层合并（同 key 覆盖）；
- 内置基座项只读，用户项带「自定义」徽标，OWL 导入项带「OWL」徽标；
- 提取弹窗/本体页 profile 列表 = 三个内置 profile + `owlProfiles`；

## 10. 领域模版 v2 重构（待实施，二期）

### 10.1 为什么保留但必须重构

**模版仍需要**——它与 profile 回答的是两个正交问题：

| | 顶层体系（profile） | 领域模版（template） |
| --- | --- | --- |
| 回答 | 用什么哲学组织知识（物体/过程、4D 时空观…） | 这个领域具体该抽什么、忽略什么 |
| 类比 | 语法 | 词汇表 + 出题范围 |
| 变化频率 | 极低（选定少动） | 随领域增减 |

现状模版（entityTypes/conceptTypes/mustExtract 等扁平字段，通用模版 + LLM 生成）与多体系机制**不匹配**：类型名是自由文本、不挂在任何体系类树上；谓词不可配；无约束；无体系绑定。因此必须重构。

### 10.2 模版数据结构 v2

```js
{
  id, name, desc, keywords[], builtin, demo?,
  ontologyProfile: 'bfo-lite',        // 绑定体系（§3 优先级 ②）
  domainClasses: [                     // 领域类 = 体系类勾选 + 扩展子类
    { key, label, parent, desc, examples[], from: 'base' | 'custom' }
  ],
  domainPredicates: [                  // 领域谓词 = 体系谓词勾选 + 领域专用
    { key, label, domain, range, features[], from: 'base' | 'custom' }
  ],
  constraints: [ {subject, attr, op, value, desc} ],  // 领域约束五元组
  mustExtract[], ignoreContent[], quality,             // 保留现有字段
  skeleton[],                          // 保留：笔记骨架
  caseRef                              // 关联演示中心（demo:true 时）
}
```

### 10.3 模版前端重构（templates 页 + 编辑器）

**模版列表页（tpl）**

- 卡片新增体系徽标 + 领域类/谓词/约束数量摘要；「演示」徽标区分 demo 模版；
- 「AI 生成模版」流程追加一步：先生成草稿 → 用户**在体系类树上勾选**确认 domainClasses（而非纯文本接受）。

**模版编辑器（tpl editor）**

- 顶部新增**体系绑定下拉**（选定后下面两个选择器随之切换数据源）；
- 「领域类」编辑器：左侧为所选体系的**类树复选框**（勾选即纳入），右侧为已选列表 + 「添加领域子类」（选 parent、填 label/desc/examples）——替代现有的 entityTypes/conceptTypes 双列表格；
- 「领域谓词」编辑器：同上模式，左侧体系谓词集复选，右侧领域专用谓词定义（label/code/domain/range 用类芯片选择）；
- 「领域约束」编辑器：五元组表格行内编辑（主体类芯片 + 属性名 + 条件下拉 + 值 + 描述）；
- mustExtract / ignoreContent / quality / skeleton 保留现有编辑控件不变；
- 保存校验：domainClasses 非空、custom 类的 parent 必须在该体系类树内、约束的 subject 必须是已选类。

**提取链路接入**

- 提取弹窗选「跟随领域模版」时：模版命中（matchTemplate）→ 其 ontologyProfile 生效，domainClasses/domainPredicates 作为 typeHints 注入提取 prompt（替代现有扁平 typeHints）；
- 模版约束在该次提取完成后自动跑一次 `validateGraphConstraints`，报告附在作业结果里（三期）。

### 10.4 迁移策略

- 旧模版加载时自动迁移：entityTypes/conceptTypes → domainClasses（挂 bfo-lite 的 object/information 下，from:'custom'），ontologyProfile 默认 bfo-lite，行为与现状完全一致；
- 迁移标记 `migratedFrom:'v1'`，编辑器首次打开时提示「已自动升级，建议确认领域类挂载位置」；
- 通用模版（id 'general'）同步升级为空 domainClasses（=不限制，退化为现有行为）。

### 10.5 与演示中心关系

每个演示即一个只读的内置模版变体（`builtin:true, demo:true, caseRef`），演示的 seedNotes/seedGraph/guideQuestions 挂在模版扩展字段上；用户可「另存为我的模版」二次编辑（复制为非 builtin 新模版）。

## 10.6 知识图谱后端重构（main 进程）

后端改动集中在 `src/main/graph/` 与 `src/main/common/constants.js`，按「谁读本体谁改」原则梳理：

### 10.6.1 constants.js：内置基座常量

### 10.6.2 graph.js：本体合成与读写路径

| 函数 | 现状 | 重构后 |
| --- | --- | --- |
| `getOntologyDef` | 直读 kv → DEFAULT_ONTOLOGY | `resolveOntology(profileId)`：内置基座/owlProfiles 深拷贝 + 用户层合并（同 key 覆盖） |
| `nodeTypesMap` | 全局一份 | 按 profileId 合成；`extractGraph`/`kgAsk` 传参指定 |
| `relationsList` | 全局一份 | 同上 |
| `fallbackType/fallbackRel` | 硬编码 'concept'/'相关' | 从生效 profile 读取 |
| `persistOntology` | 整体覆写 kv | 只写用户层（userClasses/userPredicates/userConstraints），内置基座永不落库 |
| `getOntology` | classes+predicates+constraints+stats | 返回 `{ profileId, profile:{…摘要}, classes(树), predicates, constraints, stats, owlProfiles[] }` |
| `saveOntologyItem/removeOntologyItem` | kind=classes/predicates/constraints 直改 | 操作用户层；内置 key 禁止删除（返回错误码 `BUILTIN_READONLY`） |
| `extractGraph` | 单一 prompt | 接受 `ontologyProfile` 参数 → 解析生效 profile → flat 或 two-stage prompt（§6）；节点写 `profile` 字段；二期接 domain/range 护栏 |
| `kgAsk` | 全局类型表 | 按种子节点的 profile 取对应谓词集做 BFS；事实注 `[profile·type]` 标签 |
| 新增 `importOwl(filePath)` | — | 调 owl.js 解析 → 写入 kv.owlProfiles → 返回 profile 摘要 |
| 新增 `removeOwlProfile(id)` | — | 删除 owlProfiles 项；可选连带清除该体系图谱节点 |

### 10.6.3 owl.js（新文件，二期）

- 纯 Node 实现，无外部依赖：RDF/XML 用正则+XML 解析，Turtle 用行解析；
- 输出标准化 `TopOntologyProfile` 对象（§2.4），含解析报告（类数/谓词数/跳过项/孤儿类警告）。

### 10.6.4 reason.js（新文件，三期）

四个推理器 + 影响面分析，输入 `(graph, profile)`，输出 inferred 边或冲突报告；被 kgAsk（可选启用）与演示中心调用。

### 10.6.5 ipc.js：handler 改动

- `graph:ontology`：返回结构扩展（见上 getOntology），renderer 按 profileId 缓存；
- `graph:saveOntologyItem / removeOntologyItem`：参数加 `profileId`；
- 新增 `graph:importOwl`（调 dialog 选文件 → importOwl）、`graph:removeOwlProfile`、`graph:profiles`（返回 PROFILE_LIST + owlProfiles 摘要）；
- `graph:ask`：接受 `profileScope`（'all' | profileId）；
- `raw:extractNote` / jobs 提取链路：`ontologyProfile` 参数透传（§3 优先级在 jobs 层解析一次，结果写入作业项 meta 便于展示体系徽标）。

## 11. 完整使用故事（User Story）

以下按三个核心场景说明端到端使用流程。

### 11.1 如何切换本体体系

**场景 A：浏览/编辑本体时切换**

1. 进入「知识图谱 → 本体」页；
2. 顶部 profile 切换器列出全部可用体系：`bfo-lite 简化版 BFO` / `bfo 标准 BFO 2020` / `iso15926 ISO 15926` / 已导入的 `owl:*`；
3. 点击切换 → 类树/结构图/谓词表/约束列表全部按 `resolveOntology(profileId)` 重绘；
4. 切换只影响**查看与编辑的基座**，不影响已有图谱数据（节点上的 `profile` 字段不变）；
5. 在「结构图」页签可直观对比不同体系的层级差异（如 bfo-lite 9 类 vs bfo 15 类 vs iso15926 11 类）。

**场景 B：全局默认（v4 废弃，改为 AI 自动选择）**

- v4 变更（2026-08-31）：「本体定义」页体系切换器**仅浏览/编辑**，不再兼任全局默认。抽取时由 AI 按内容自动选择合适体系（领域模版绑定优先，兜底 bfo-lite）；问答直接遍历图谱节点（节点带 `profile` 字段区分体系）。用户无需手动切换体系。

**场景 C：为领域模版绑定体系**

- 模版编辑器中 `ontologyProfile` 字段选择体系（二期）；使用该模版提取时自动带上对应体系，无需每次手选。

**场景 D：导入自定义体系后切换**

- 「本体 → 导入 OWL」选择本地 `.owl/.rdf/.ttl` 文件 → 解析完成出现在切换器列表（带「OWL」徽标）→ 点击即可切换查看其结构图，确认解析无误后用于提取。

### 11.2 如何使用本体进行问答

以提问「光猫断电会影响哪些设备和服务？」为例（图谱为演示 D4 家庭网络，bfo-lite 体系）：

1. **进入问答页**：「知识图谱 → 问答」，输入问题；
2. **实体识别**：LLM 从问题中抽取提及实体（如「本地缓存服务器」），kgAsk 在图谱中按名称匹配种子节点；
3. **体系感知扩展**：种子节点的 `profile` 决定遍历语义——沿该体系的谓词做 BFS（bfo-lite 下沿「依赖/包含」等；iso15926 下沿 `connectedTo / involvedIn / temporalPartOf` 等），hop 数默认 3 可调；
4. **类型标签上下文**：收集到的事实三元组带上体系标签注入 prompt，形如 `[bfo-lite·object] 光猫 —依赖→ NAS —依赖→ 家庭监控`，LLM 据此理解节点的本体角色（是物体还是过程），减少答非所问；
5. **引用回溯**：答案末尾列出引用来源（笔记/原始文件），与现有 collectRefs 机制一致；
6. **混合体系问答**（二期映射表启用后）：种子节点为 bfo-lite 类型时，经映射表（object ↔ physical_object）可对齐到 iso15926 子图继续扩展，答案中注明跨体系对齐路径。

约束校验类问题（如「我们小区充电桩扩容方案超出变压器容量上限了吗？」）在三期可由 validateGraphConstraints 先跑约束五元组，再把违规/满足项作为事实注入答案。

### 11.3 如何使用本体抽取知识图谱

**标准流程（以提取一份 PDF 为例）**

1. 「原始文件」页选中文件 → 点击「提取图谱」；
2. 弹窗中选择：
   - **领域模式**：手动选模版 / 自动匹配（模版可预绑定体系）；
   - **本体体系**：下拉四项——`跟随领域模版`（默认）/ `bfo-lite` / `bfo` / `iso15926` / 已导入的 `owl:*`；
3. 确认后进入作业队列，作业项上显示所用体系徽标；
4. **提取执行**：
   - bfo-lite：单阶段 prompt，一次性给出 9 类类型表 + 中文谓词表；
   - bfo / iso15926：两阶段 prompt——先判 continuant/occurrent（或 possible_individual/abstract_object）大类，再在子树内细分叶子类型；
   - 谓词受所选体系约束（bfo 用 RO 的 part_of/participates_in 等，iso15926 用 Part 7 模板谓词），domain/range 护栏校验不通过的边降级为兜底关系并记日志（二期）；
5. **结果落库**：节点带 `profile` 字段与体系类型；同一份文档用不同体系重复提取会按体系分别生成节点（nodeKey 含 profile 前缀，互不覆盖），便于对比；
6. **查看结果**：
   - 「图谱」页按 profile 分组着色浏览，类型筛选器按体系分组；
   - 「本体 → 结构图」对照该体系应然层级，检查提取结果是否符合体系约束（如出现 iso15926 下不该有的类型则标黄）；
7. **迭代优化**：发现某类文档用 bfo-lite 提取粒度过粗 → 改用 iso15926 重新提取同一份文件，对比两版图谱后保留更优者（另一版可通过图谱页「按体系清除」删除）。

**OWL 自定义体系提取**（二期）

导入 OWL → 结构图确认 → 提取弹窗选择该 `owl:*` 体系 → 提取流程与内置体系一致（promptMode 按类数自动判定），提取结果的节点类型即 OWL 中的类。

### 13.2 体系解析优先级（实际实现，覆盖 §3 文字）

`graph.js extractGraph` 中生效体系的解析顺序为：

```
弹窗显式 ontologyProfile  >  命中领域模版的 ontologyProfile（resolveDomain 回填；
指定已有领域时主动读模版绑定）  >  settings.ontologyProfile（历史全局默认，v4 起 UI 不再写入）  >  bfo-lite
```

与 §3 的差异：② 的实现包含「指定已有领域（跳过匹配）时主动读取该领域模版绑定体系」的兜底分支——§3 未写明此分支，补充于此，防止「选了领域却丢了模版体系」。

> v4 说明（2026-08-31）：本体定义页体系切换器改为**仅浏览/编辑**（写 kv.profileId 只服务本页展示与用户自定义叠加的编辑），**不再作为抽取的全局默认**；抽取/问答所用体系由 AI 按内容/模版绑定自动选择，实际流程命中上式前两级，后两级仅作兜底。

### 13.3 角色分工（人 / LLM / 系统）

§0 的例子以第二人称叙述，容易让读者误以为系统已具备全流程自动合规能力。实际分工：

- **用户（立规矩、做裁决）**：选体系、勾领域类/谓词、定义约束、裁决冲突（六态机的人工升级终点）；
- **LLM（提议者，非裁决者）**：在体系类表/谓词表划定的范围内归类与连线（§0.2 ①），产出带置信度的候选断言；约束校验、推理闭包等**确定性计算不交给 LLM**，由系统执行（三期）；
- **系统（守门与计算）**：fallback 降级、去重/禁自环、profile 打标、护栏校验（二期）、约束硬校验与推理器（三期）。

**对照 §0.0「充电桩扩容」例子的角色映射**：

| 例子中的角色 | 现实身份 | 系统角色 |
| --- | --- | --- |
| 你 | 业主/住户一方 | **用户**：选体系、建领域类、定约束、裁决结果（立规矩、做裁决） |
| 物业 | 小区物业管理方 | **外部资料提供方/需求触发者**：只递交文档，不操作系统 |
| 三份文档 | 《供电容量说明》等 | **原始文件（raw）**：提取流水线的输入 |
| LLM | — | 按体系类表/谓词表归类连线，产出候选三元组（提议者） |
| 系统 | — | fallback 降级、去重、约束硬校验、推理补全（守门与计算） |

原则：**凡可形式化的规则（约束、特性推理）一律系统执行；LLM 只负责开放语义（归类、连线、摘要）**。

### 13.4 已知不足与后续修订方向

1. **护栏缺失期的数据污染**：domain/range 护栏未实现前，LLM 越界连线仅靠 fallbackRel 兜底，混合体系图谱中 `相关/relatedTo` 兜底边会偏多——概览页「体系健康度」行（§7.2）应同时统计「兜底关系边占比」作为质量信号；
2. **两阶段 prompt 无回退重试**：阶段一判错大类时，阶段二在错误子树内细分无纠偏机会——后续可加「阶段二置信度低时回退全表单阶段」的保险丝；
3. **OWL 导入无增量重解析对比**：重新导入（§7.2）当前为整体覆盖，后续应输出 diff（新增/删除类）并提示对既有图谱节点的影响（type 失联标黄）；
4. **演示中心与约束/推理强耦合**：§9 的 D3/D5/D6 依赖三期能力（推理器、约束校验），若三期延期，演示中心应先落地 D1/D2/D4/D7/D10 等仅依赖一期能力的演示，避免「演示承诺超出产品能力」；
5. **类数基数漂移**：constants.js 的体系类/谓词会随调优增减（v3 实测 bfo-lite 11 / bfo 21 / iso 14），文档不再逐版本追数，以本体定义页结构树展示为准。
