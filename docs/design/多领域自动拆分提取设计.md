# 多领域自动拆分提取 · 总体设计

> 分支：`multi-domains-auto-gen` ｜ 状态：v1.1（开放问题已决议，待实现） ｜ 日期：2026-09-05
>
> 需求：当一个目录/一批来源**混合了多个互不相关的领域**（例如同时含「充电桩扩容工程」与「细胞代谢研究」）时，提取知识图谱不再把它们塞进同一个领域，而是：
>
> 1. AI 识别出全部内聚领域；
> 2. **AI 逐文件分类**，判断每个原始文件属于哪个领域；
> 3. 每个领域**匹配或新建**各自的领域模版、各自匹配本体体系；
> 4. 每个领域**单独提交一个图谱提取作业**，且该作业**只跑属于该领域的文件子集**。

---

## 0. 背景与问题

### 0.1 现状（单领域流程）

`autoDomainAndExtract()`（`src/renderer/raws.js`）当前流程：

```
① 领域匹配（checkDomainBeforeIngest → tpl:matchFor）
   ├─ 命中已有领域 → 用之
   └─ 未命中 → ② 归纳并新建一个领域（tpl:suggestName → tpl:generate → tpl:save）
② 体系匹配（tpl:suggestProfile，或复用模版绑定）
③ 确认卡片（一个领域下拉 + 一个体系下拉）→「确认提取」
   → 提交一个 graph 作业（payload.rawPaths = 全部来源）
```

**问题**：来源是混合多领域时，AI 只能归纳出**一个**「最贴合」的领域。截图实例中，7 个文件包含充电桩报装、供电容量、施工安全、**细胞代谢研究报告**四类内容，归纳出的领域必然顾此失彼——细胞代谢的实体被硬套进工程领域模版的类型约束里，图谱被污染。

### 0.2 关键决策（已与用户对齐）

| 决策点 | 结论 | 备选（未采用） |
|---|---|---|
| 文件是否按领域拆分 | **拆分**：LLM 逐文件分类，每个作业只跑该领域文件子集 | 不拆分（各作业跑全部文件，仅靠 typeHints 区分） |
| 确认界面形态 | 多领域**清单一次确认**：每个领域一行（名称/文件数/体系），可勾选，一次「确认提取」批量提交 | 逐领域逐个弹窗确认 |
| 领域数量上限 | **5 个**，防 AI 过度拆分导致作业爆炸 | 3 个 / 不限 |

拆分的理由：类型约束（typeHints）只对「该领域的实体」有效，混入异领域文件时，LLM 要么漏抽（类型对不上）、要么错抽（强行归类）。拆分后每个作业的 prompt 上下文更纯粹，抽取质量更高；代价是分类阶段多一次 LLM 调用。

## 1. 总体流程

```
用户选中目录/多文件 →「提取知识图谱」
  │
  ① 多领域识别    tpl:suggestDomains      → [{name, desc}]（≤5）
  │
  ② 逐文件分类    tpl:assignDomains       → { assignments: {rawPath: {domains: [...], confidence}}
  │                                              unassigned: [] }
  │                                              （文件可同时归属多个领域，带置信度）
  │
  ③ 逐领域准备    对每个领域：
  │    ├─ 模版：同名已有 → 复用；否则 tpl:generate + tpl:save 新建
  │    └─ 体系：模版绑定优先；无绑定 → tpl:suggestProfile 按该领域文件子集内容匹配
  │
  ④ 确认清单      每领域一行：☑ 领域名（下拉可改）｜n 个文件｜体系（下拉可改）｜✕ 移除
  │               「确认提取」→ 批量提交
  │
  ⑤ 批量提交      每个勾选领域 → 一个 graph 作业
                  payload.rawPaths = 该领域文件子集, autoDomain=false
```

退化规则：识别结果只有 1 个领域时，流程与现状完全一致（清单只有一行）。

## 2. 主进程设计（templates.js）

### 2.1 `suggestDomains(settings, raws, onDelta)` — 多领域归纳

一次 LLM 调用返回领域数组。与现有 `suggestTemplateName` 的区别：提示词明确要求「识别所有内聚领域」并返回数组。

```javascript
// 返回 { domains: [{ name, desc }] }，1~5 个，同名去重
async function suggestDomains(settings, raws, onDelta) {
  const text = raws.map((r) => r.content).join('\n').slice(0, 4000);
  // prompt 要点：
  // - 内容围绕单一主题 → 只返回一个领域
  // - 明显混合多个不相关主题 → 返回多个
  // - 最多 5 个；名称 2-8 汉字，内聚、不过宽
  // 输出：{ "domains": [ { "name": "...", "desc": "..." } ] }
  // 兼容单对象返回 {name, desc} → 包成单元素数组
}
```

- **上限 5**：`.slice(0, 5)` 硬截断；同名去重。
- **导出**：加入 `module.exports`。

### 2.2 `assignDomains(settings, raws, domains)` — 逐文件分类（多归属 + 置信度）

> 这是本方案相对「不拆分」新增的核心步骤。v1.1 起允许**一个文件同时归属多个领域**，并返回 **per-file 置信度**。

```javascript
// 入参：raws = [{ rawPath, content }]，domains = [{ name, desc }]
// 返回 {
//   assignments: { [rawPath]: { domains: [领域名, ...], confidence: 0.0~1.0 } },
//   unassigned: [rawPath]
// }
async function assignDomains(settings, raws, domains, onDelta) {
  // 1. 构造清单：每个文件取「文件名 + 内容前 300 字」作为判据，
  //    避免全文注入导致 prompt 爆炸（N 文件 × 全文）
  // 2. prompt：给定领域清单（名称+描述），逐文件判定归属；
  //    输出 { "assignments": { "<rawPath>": { "domains": ["领域A"], "confidence": 0.92 } } }
  //    - 每文件归入一个或多个领域（domains 为数组，≥1 个）
  //    - 同时涉及多个领域（如「充电桩对电网负荷的影响」兼工程与科研）→ domains 列多个
  //    - confidence：对该归类的把握（0~1）；多归属时取整体把握
  //    - 无法判定的文件放进 "unassigned": []
  // 3. 解析校验：domains 数组中每个名字都必须在给定领域内，非法名字剔除；
  //    剔除后数组为空 → 该文件移入 unassigned；confidence 越界钳制到 [0,1]
}
```

**多归属的去重策略**（决策 1 的落地）：文件进多组后，同一物理文件会被多个作业各跑一遍，可能在不同领域图谱中产生**同名/同实体**节点。去重不在分类阶段做，而放在**图谱写入层**——graph 作业落库时按 `(profile, 实体规范化名)` 做边级合并（同 profile 下重名实体合并属性与关系，跨 profile 不合并、属不同图谱视图）。本设计只保证「不丢文件」，实体级去重依赖既有/后续的图谱合并能力，不在本次改动范围。

**置信度用途**：仅用于**展示**——清单中低置信（< 0.6）文件的归属行标「?」提示用户人工核对；不参与自动改判（避免阈值拍脑袋）。

**批量策略**：
- 文件数 ≤ 20：一次调用全部判定。
- 文件数 > 20：按 20 个一批**分批调用**（防超时、防输出截断），合并结果。每批带相同领域清单。
- 单领域时**跳过本步**，全部文件直接归该领域（省一次 LLM 调用），confidence 记 1.0。

**unassigned 处理**：无法分类的文件归入**「通用」组**——不为其新建模版，用 `general` 模版 + 默认体系单独成一个作业，出现在确认清单末尾且**默认勾选**（宁多勿漏，用户可取消勾选放弃）。

### 2.3 领域模版准备（复用现有函数）

对每个领域名：

```
tpl = listTemplates().find(name 精确匹配 && id !== 'general')
if (!tpl) {
  gen = generateTemplate(settings, { name, desc })   // 现有：体系绑定+领域类
  id 冲突时加 _xxxx 后缀
  tpl = saveTemplate({ ...gen, name, desc })
}
```

体系：优先 `tpl.ontologyProfile`；为空时 `suggestOntologyProfile(settings, 该领域文件子集)` ——注意此处 **raws 用该领域的文件子集**而非全集，体系匹配更准。

## 3. IPC 与 preload

### 3.1 新增 handler（`src/main/ipc.js`）

| channel | 入参 | 返回 | chunk 事件 |
|---|---|---|---|
| `tpl:suggestDomains` | `{ settings, rawPaths, texts }` | `{ ok, domains }` | `tpl:suggest-domains-chunk` |
| `tpl:assignDomains` | `{ settings, rawPaths, domains }` | `{ ok, assignments, unassigned }` | `tpl:assign-domains-chunk` |

`assignments` 的值结构为 `{ domains: [...], confidence }`（见 §2.2）。两者都经 `buildMatchRaws` 构造 raws（注意：assignDomains 需要按 rawPath 归组，不能丢路径标识）；onDelta 流式增量推送思考过程。

### 3.2 preload 暴露

```javascript
tplSuggestDomains:  (p) => ipcRenderer.invoke('tpl:suggestDomains', p),
tplAssignDomains:   (p) => ipcRenderer.invoke('tpl:assignDomains', p),
onTplSuggestDomainsChunk: (cb) => { /* tpl:suggest-domains-chunk */ },
onTplAssignDomainsChunk:  (cb) => { /* tpl:assign-domains-chunk */ },
```

## 4. 渲染层设计（raws.js）

### 4.1 数据结构

`autoDomainAndExtract` 内的单领域 `sel` 改为数组：

```javascript
// 每个元素对应一个待提交作业；同一文件可出现在多个组的 fileRefs 里（多归属）
const groups = [
  {
    key: 'domain_1',          // 领域名或 'general'
    domainId: 'ev_charging',  // 模版 id
    tpl,                      // 模版对象（含 domainClasses → typeHints）
    profileId: 'iso15926',
    // 本组文件子集，逐文件带置信度，供清单标「?」
    fileRefs: [{ rawPath: 'raw/供电容量说明.md', confidence: 0.95 }, ...],
    inlineSources: [...],                    // 笔记场景见 §4.4
    checked: true,
  },
];
```

### 4.2 判定流程（卡片流）

```
卡片①「识别来源包含的领域」 running → done
  └─ 徽章：「3 个领域」充电桩扩容、细胞代谢、……
卡片②「逐文件归类」 running → done
  └─ 每文件一行 note：供电容量说明.md → 充电桩扩容
卡片③「准备领域模版与体系」 running → done
  └─ 每领域一行 note：✔ 充电桩扩容 → 模版「充电桩扩容」/ 体系「ISO 15926」
卡片④ 确认清单（见 §4.3）
```

思考流容器沿用现有 `mkThink`/`feedThink`/`collapseThink` 机制，订阅新增的两个 chunk 事件（多领域归纳、文件归类）。

### 4.3 确认清单 UI

替换现有 `finalizeDecision` 的单下拉卡片为**分组清单**：

```
┌─ ✔ 请确认提取配置（将为每个勾选领域各提交一个作业） ─┐
│ ☑ [领域: 充电桩扩容 ▾]  3 个文件  [体系: ISO 15926 ▾]  ✕ │
│      └ 供电容量说明.md 0.95 ｜ 施工安全.md 0.88 ｜ 负荷研究.md 0.52? │
│ ☑ [领域: 细胞代谢   ▾]  2 个文件  [体系: BFO 2020   ▾]  ✕ │
│      └ 代谢研究报告.md 0.97 ｜ 负荷研究.md 0.52?（同文件亦在充电桩组）│
│ ☑ [通用（未分类）  ]  1 个文件  [体系: BFO-Lite    ▾]  ✕ │  ← 默认勾选
└──────────────────────────────────────────────┘
              [取消]            [确认提取]
```

- 勾选框控制该组是否提交；✕ 等价于取消勾选并折叠。
- 领域下拉切换为另一已有模版时，typeHints 随之切换；文件归属**不变**（文件分类是内容级的，不随模版选择变化）。
- **置信度标记**：每行文件后附 confidence；`< 0.6` 的低置信项标橙色「?」，鼠标悬停提示「归类把握较低，请人工核对」。只提示、不自动改判。
- **多归属提示**：同一文件出现在多个组时，在其明细后标注「同文件亦在 X 组」，让用户意识到该文件会被提取多次。
- 「通用（未分类）」组**默认勾选**（宁多勿漏），用户可取消勾选放弃。
- 底部提示改为：「勾选要提取的领域，点「确认提取」将为每个领域各提交一个作业」。

### 4.4 inlineSources（笔记图谱）的处理

笔记内联来源 `{label, text}` 没有稳定「文件路径」，但同样可分类：
- 分类键用 `label`；判据取 `label + text 前 300 字`。
- 分组后每作业 `payload.inlineSources = 该组子集`。
- `tpl:assignDomains` 的 raws 构造侧：`rawPath` 填 `inline:<label>`，assignments 的键按此回映射。

### 4.5 提交循环

```javascript
const doSubmitAll = async () => {
  const targets = groups.filter((g) => g.checked && (g.fileRefs.length || g.inlineSources.length));
  if (!targets.length) { toast('请至少勾选一个领域'); return false; }
  let ok = 0;
  for (const g of targets) {
    const extras = graphDomainExtras({ id: g.domainId, name: g.tpl?.name || '通用', tpl: g.tpl });
    extras.autoDomain = false;                    // 领域/体系已定，作业内不再判定
    if (g.profileId) extras.ontologyProfile = g.profileId;
    if (g.inlineSources.length) extras.inlineSources = g.inlineSources;
    else extras.rawPaths = g.fileRefs.map((f) => f.rawPath);  // ★ 只跑该领域文件子集
    if (await submitJobPayload(extras)) ok++;
  }
  return ok > 0;
};
```

作业卡片标题沿用 `知识图谱抽取·<文件名…>`；领域徽标经 `job.source.domain` 展示（现有机制，无需改动）。

## 5. 边界与容错

| 场景 | 处理 |
|---|---|
| 只识别出 1 个领域 | 跳过文件分类（§2.2），清单只有一行，行为与现状一致 |
| 分类后某领域 0 个文件 | 该领域不进入清单（不建空作业）；其模版若已新建则保留（用户可在模版管理删） |
| 全部文件 unassigned | 回退现状：单组「通用」+ 全集文件 |
| suggestDomains 失败/超时 | 回退单领域路径（现有 `autoCreateDomainNow` 逻辑），保证不阻断 |
| assignDomains 部分批次失败 | 该批文件全部进 unassigned（通用组），不丢文件 |
| 同名模版已有 | 复用，不重复生成（与现逻辑一致） |
| 用户在判定中点「取消」 | `cancelled=true`，中断后续 LLM 调用与清单渲染（现机制沿用） |

**覆盖完整性不变式**（替代 v1 的文件守恒）：`各组文件并集 + unassigned = 总来源集`——每个文件至少被一个组覆盖或进入 unassigned，**不允许丢文件**；但因多归属，文件可在组间重复。渲染层提交前断言「并集覆盖全集」，不满足则回退「单组通用 + 全集」。实体级去重不在此断言范围（见 §2.2 去重策略）。

## 6. 性能与限额

- LLM 调用次数：1（领域归纳）+ ⌈N/20⌉（文件分类）+ Σ新建领域数（gen，每域 2 次）+ Σ无绑定体系数（profile）。典型 3 领域、7 文件场景 ≈ 1+1+0~6+0~3 次。
- 领域匹配/分类均属轻量判定：`thinkingBudget` 沿用 4000 上限；分类 prompt 注入文件摘录而非全文。
- 作业提交为顺序循环（每作业一次 `jobs:submit` IPC），N ≤ 6 时无并发压力。

## 8. 已决议的开放问题

1. **跨领域文件**：一份文件同时讲两个领域（如「充电桩对电网负荷的影响研究」兼工程与科研）？→ **允许多归属**：`assignments` 的 `domains` 为数组，文件同时进多个组、被多个作业各提取一次。由此可能在不同领域图谱中产生同名实体，**去重策略放在图谱写入层**——graph 作业落库时按 `(profile, 实体规范化名)` 做边级合并（同 profile 重名实体合并，跨 profile 属不同图谱视图、不合并）。清单中对多归属文件标注「同文件亦在 X 组」让用户知情。实体级去重的具体实现不在本次改动范围，依赖既有/后续的图谱合并能力。
2. **unassigned 的默认勾选**：→ **默认勾选**（宁多勿漏），用户可在清单取消勾选放弃。
3. **分类置信度**：→ **做**。LLM 返回 per-file `confidence`，清单每行文件后展示该值，`< 0.6` 的低置信项标橙色「?」提示人工核对；仅作展示，不参与自动改判。
