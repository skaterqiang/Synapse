# 新需求校验与功能影响分析

用 `graph/his-graph.json` + `ontology/his.ttl`，对"新增 / 下线 / 改造"某类 HIS 需求做**影响面校验**。影响面沿传递谓词 `dependsOnFunction`（功能依赖）与 `callsService`（服务调用）计算，数据层用 `readsWrites` 反查；口径与应用「实体详情·影响面」和 `reason/impact.js` 一致。可直接运行：

```bash
node tools/validate-impact.js                 # 跑下面 4 个场景并自检（应全部 PASS）
node tools/validate-impact.js 挂号 affects     # 自由查询某功能的影响下游
node tools/validate-impact.js 对账结算 depends # 查某功能的上游依赖闭包
```

## 场景 A：下线「医技诊疗项」功能（医技医生工作站核心）

沿 `dependsOnFunction` 反查"谁依赖它"（含传递）：

- L1：`收缴费`（收缴费依赖医技诊疗项）
- L2：`退费`、`对账结算`（经收缴费间接依赖）
- 校验结论：下线医技工作站前，必须先处理收费/退费/结算对"非药品诊疗项"的引用，否则收费流程悬空。

## 场景 B：改造 / 删除枢纽「挂号」

挂号是跨域枢纽，沿依赖闭包波及面最大：

- L1：`就诊病历`、`收缴费`
- L2：`开方`、`医技诊疗项`、`退费`、`对账结算`
- L3：`药房发药`
- 校验结论：挂号结构（`dms_registration`）任何变更都是**高影响面**动作，需回归除系统管理外的几乎全部诊疗/财务功能。

## 场景 C：修改数据实体 `dms_medicine_prescription_record`（成药处方）

先用 `readsWrites` 反查"哪些功能读写这张表"：

- L1：`开方`、`药房发药`
- 再叠加场景 A/B 的机制：`开方`被波及会进一步传导到 `收缴费 → 退费/对账结算`。
- 校验结论：给成药处方加列/改类型，至少同步改造开方与发药功能，并评估收费链路。

## 场景 D：新增「医保结算」功能（新增类校验）

医保结算落在财务域，接入图谱应：

1. 新建节点 `医保结算 : FinanceModule`；
2. 补 `dependsOnFunction` 边：→ `收缴费`（在收费基础上做医保分流）、→ `患者管理`（读参保人）；
3. 补 `hostedOn`：→ `service-bms`；`includes`：对帐员工作站 → 医保结算；
4. 补 `readsWrites`：医保结算 → `bms_bills_record`、→ 新增实体 `医保结算记录`；
5. 用 `depends` 模式校验其上游节点均存在且类型合法（Finance 依赖 Finance/Patient，符合本体 domain/range）；
6. 反向用场景 A/B 校验：新功能只新增自身被引用边，不改动既有节点影响面。

## 校验方法与判据

| 校验项 | 依据（his 本体） | 通过标准 |
|---|---|---|
| 功能类型合法 | `Clinical/Drug/Finance/Patient/System Module ⊑ FunctionModule` | 功能节点 type 取自五者之一 |
| 依赖方向正确 | `dependsOnFunction : FunctionModule → FunctionModule` | 两端均为功能模块 |
| 承载服务合法 | `hostedOn : FunctionModule → Service` | 每个功能≥1 条承载边 |
| 读写实体在模型内 | `readsWrites : FunctionModule → DataEntity` | 目标实体节点存在（无悬空表） |
| 无孤立模块 | `includes : Workstation → FunctionModule` 覆盖 | 每个功能至少被一个工作站包含 |
| 影响面可计算 | `dependsOnFunction`、`callsService` 为 TransitiveProperty | `validate-impact.js` 非空且场景自检全 PASS |

> 说明：本样例影响面为**自包含脚本**，与应用内 `reason/impact.js`（同样沿传递谓词 BFS + 反向求消费者）逻辑一致；应用侧导入 `his.ttl` 后，可在"整体图谱·影响面/校验"获得等价结果。与"使用 GSM 验证 HIS 新功能"的对应：此处以知识图谱做需求影响校验（GSM 理解为需求/影响管理环节），未引入外部体系。
