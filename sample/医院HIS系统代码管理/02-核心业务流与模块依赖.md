# 核心业务流与模块依赖

本篇从 `code/` 里的**真实源码**还原业务流，并给出知识图谱里 `dependsOnFunction`（依赖功能）边的取证依据。影响面分析正是沿这条传递谓词展开。

## 挂号流（跨 DMS / SMS / PMS / BMS）

证据：`code/services/DmsRegistrationService.java` 的 `appRegistration` 方法注释原文——

```
1. 先根据 skd_id 判断 remain 是否 > 0                       // 读 sms_skd 号源
2. 如果大于0，绑定医生(skd_id, bind_status=1)，并修改 sms_skd 中的排班限额(-1)  // 写 sms_skd
3. 向 dms_registration 插入信息                              // 写 dms_registration
4. 向 bms_bills_record 中插入账单记录                        // 写 bms_bills_record
```

再配合实体 `DmsRegistration.java` 的字段 `patientId / skdId / deptId`，可确定：

- **挂号 依赖 排班**（占号源）、**挂号 依赖 患者管理**（就诊人）；
- 挂号 写 `dms_registration`、`bms_bills_record`，读 `sms_skd`、`pms_patient`。

挂号因此成为串联"患者域 / 系统域 / 财务域"的**枢纽功能**。

## 收缴费 / 退费流（以挂号 id 为主线）

证据：`code/services/BmsFeeService.java` 方法签名——

| 方法 | 含义 | 得到的依赖 |
|---|---|---|
| `listRegisteredPatient` / `listChargeByRegistrationId` | 按挂号 id 查未缴费项目 | **收缴费 依赖 挂号** |
| `charge` | 收费，写账单/发票 | 读写 `bms_bills_record` |
| `refundCharge` | 非药品、药品退费 | **退费 依赖 收缴费**、退费 依赖 药品管理 |
| `refundRegistrationCharge` | 挂号退费（回退号源） | 退费读 `dms_registration`/`sms_skd` |

## 开方 → 发药流（临床诊疗 → 药品管理）

`DmsMedicinePrescriptionRecord` / `DmsHerbalPrescriptionRecord` 携 `registrationId` 依赖挂号、引用 `dms_drug`；处方转账单进入收费；药房发药按处方发药并扣库存。故 **开方 依赖 就诊病历、药品管理**；**药房发药 依赖 开方、药品管理**。

## 对账 / 日结流（财务）

`BmsOperatorSettleRecord`（操作员结算/日结）汇总当日收缴费流水——**对账结算 依赖 收缴费**。

## 依赖功能边汇总（`graph/his-graph.json` 的 `dependsOnFunction`）

```
挂号        ─依赖→ 排班, 患者管理
就诊病历    ─依赖→ 挂号, 患者管理
开方        ─依赖→ 就诊病历, 药品管理
药房发药    ─依赖→ 开方, 药品管理
医技诊疗项  ─依赖→ 就诊病历
收缴费      ─依赖→ 挂号, 开方, 医技诊疗项
退费        ─依赖→ 收缴费, 药品管理
对账结算    ─依赖→ 收缴费
```

端到端主链路：`挂号 → 就诊/病历 → 开方(药/非药) → 收费 → 发药/执行 → 对账结算`。链路上任一环节被改造，其所有**上游依赖方**（经传递闭包）都需回归——下一篇（笔记 03）用图谱量化这些影响面。
