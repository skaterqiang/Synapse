# 新需求校验与指标影响分析

用 `graph/dw-metric-graph.json` + `ontology/dw-metric.ttl`，对"新增 / 删除 / 修改"某类需求做**影响面校验**。影响面沿传递谓词 `dependsOn`（指标依赖）与 `processedFrom`（血缘）计算，与应用「实体详情·影响面」和 `reason/impact.js` 口径一致。可直接运行：

```bash
node tools/validate-impact.js            # 跑下面 4 个场景并自检
node tools/validate-impact.js 下单订单数   # 自由查询某节点的影响下游
```

## 场景 A：删除原子指标「下单订单数」

- 沿 `dependsOn` 反查"谁依赖它"（含传递）：
  - L1：`支付成功率`、`退款率`
  - L2：`客单价健康度`（经 支付成功率 间接依赖）
- 校验结论：`下单订单数` 不可直接删除；如确需下线，必须同时重定义上述 3 个上层指标，或先解除其 `dependsOn` 边。

## 场景 B：DWD 明细表 `dwd_order_detail` 口径变更（如新增 status=partial_refund）

- 沿 `processedFrom` 反查血缘下游：
  - L1：`dws_trade_user_1d`、`dws_trade_city_1d`、`adm_overview_1d`
- 结合笔记 02「口径红线」：所有以 `status` 过滤的原子指标（支付订单数/支付金额/退款金额）需重定义，其派生指标（支付成功率/客单价/退款率）随场景 A 机制继续放大。
- 校验结论：明细层字段口径变更是**高影响面**动作，需回归 DWS→ADM 全部加工任务。

## 场景 C：下线派生指标「客单价」

- 沿 `dependsOn` 反查：
  - L1：`客单价健康度`
- 校验结论：下线"客单价"前需先处理"客单价健康度"（删除或改造），否则该复合指标悬空。

## 场景 D：新增需求「退款金额占比」指标（新增类校验）

新指标"退款金额占比 = 退款金额 / 下单金额"应如何接入图谱：

1. 新建节点 `退款金额占比 : DerivedMetric`；
2. 补两条 `dependsOn` 边：→ `退款金额`(AtomicMetric)、→ `下单金额`(AtomicMetric)；
3. 用 `depends` 模式校验其上游都在图谱内且类型合法（Derived 依赖 Atomic，符合本体）；
4. 再用场景 A/B 反向校验：新指标不改变既有节点的影响面，仅新增自身被引用；
5. 落库前过写侧护栏：`dependsOn` 的 domain/range 均为 `Metric`，两端类型匹配，通过。

## 校验方法与判据

| 校验项 | 依据（dw-metric 本体） | 通过标准 |
|---|---|---|
| 指标类型合法 | `AtomicMetric/DerivedMetric/CompositeMetric ⊑ Metric` | 指标节点 type 取自三者之一 |
| 依赖方向正确 | `dependsOn : Metric → Metric` | 两端均为指标节点 |
| 血缘方向正确 | `processedFrom : LayerTable → LayerTable` | 两端均为分层表 |
| 原子指标有来源 | `sourcedFromTable : Metric → LayerTable` | 每个原子指标≥1 条来源边 |
| 影响面可计算 | `dependsOn`、`processedFrom` 为 TransitiveProperty | `validate-impact.js` 非空且场景自检全 PASS |

> 说明：本样例的影响面计算为**自包含脚本**，与应用内 `reason/impact.js`（同样沿传递谓词 BFS）逻辑一致；应用侧可导入 `dw-metric.ttl` 后，在"整体图谱·影响面/校验"获得等价结果。
