# 多源系统集成方案（OBDA）

## 一、背景

集团下属炼化装置的设备数据分散在四套源系统中：MES（制造执行系统）、EAM（设备资产管理）、DCS（集散控制系统）、CMMS（维修管理）。各系统对同一台设备的命名、编码、层级划分都不一致，跨系统查询需要人工对照，效率极低。

本方案采用 OBDA（Ontology-Based Data Access，基于本体的数据访问）：不搬迁数据，而是把各源系统的表/接口映射到一个统一的「设备领域本体」上，查询在本体层提出，由查询重写引擎下推到各源系统执行。

## 二、统一本体骨架

以 ISO 15926 的 4D 时空观组织：

- **物理对象（physical_object）**：装置、机组、设备、部件。装置由机组组成，机组由设备组成，设备由部件组成（composedOf 传递）。
- **活动（activity）**：运行、检修、巡检等活动。设备参与活动（involvedIn）。
- **事件（event）**：停机、报警、故障等时间点事件。事件发生于某台设备。
- **时间段（period_in_time）**：检修周期、运行班次。
- **类（class）**：设备型号、设备类别等分类节点。个体设备归类于设备型号（classifiedBy）。

## 三、源系统映射

| 源系统 | 提供数据 | 映射到本体 |
|---|---|---|
| MES | 装置-机组-设备层级、生产批次 | 物理对象的 composedOf 层级 |
| EAM | 设备台账、型号、位置、责任人 | 物理对象个体 + classifiedBy |
| DCS | 实时测点、报警事件 | 事件 + 时间段 |
| CMMS | 检修工单、备件消耗 | 活动 + involvedIn |

## 四、查询重写要求

大数据量下要求查询可重写为 SQL 下推执行，因此本体表达力限定在 OWL 2 QL profile 内；设备型号的分类推理（如「离心泵 ⊑ 泵 ⊑ 旋转设备」）限定在 OWL 2 EL profile 内。发布前用 profile 检查器确认本体没有超出对应 profile 的表达力。

## 五、一致性要求

同一台设备在不同源系统中的记录，通过统一设备编码（tag number）对齐。若两条记录编码相同但型号不同，视为映射冲突，必须在集成前消解。
